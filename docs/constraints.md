## Constraints 
| Constraint | Description | Engineering Implication |
| :--- | :--- | :--- |
| Team Size and Resources | The project must be completed by a team of only 3 members. | Because development resources are limited, we must avoid complex architectures that require more overhead. If one team member falls behind, the other two will do the workload, which means code must be readable and documented. |
| Schedule | The project must progress through 4 formal milestones within 7 weeks. | Time is heavily limited, so scope must be flexible. If a chosen technology is too difficult to learn or if development falls behind the schedule, then we must drop the “could have” and “should have” features rather than to miss a milestone’s deadline. |
| Cost | The team must use free services where possible and identify operational limits. | This heavily restricts our tech stack for M2. We cannot use premium services. We must actively monitor our usage of free limits to ensure we do not hit a paywall. |
| Scope control | Committed scope must be baselined, uncontrolled scope creep is not acceptable. | Once M1 document is signed off, any new feature ideas cannot be silently added. It must go through a formal Change Request and impact analysis to ensure it does not interfere with our schedule or quality. |
| Evidence | Attributes must be defined and later supported by measurable evidence and not just claims. | We cannot just simply say the code works; we must prove it. This is implied we must allocate time to write automated test and configure continuous integration pipeline to act as a quality gate before any code merges into the main branch. |
| Security | Security must be treated as a lifecycle wide engineering responsibility not just a final add-on. | We must implement strict config management from day one. Things like database passwords and API keys must never be committed to our GitHub. This does require us to establish a secure environment strategy. |
| Technology and team capability | No technology stack is prescribed but decisions must be justified against the constraints and our team capability. | We cannot pick a popular framework just because it looks trendy. If we pick a tech stack that nobody in the team knows there is a learning curve risk and that will threaten our schedule. |
