# Requirements & Acceptance Criteria
## Functional Requirements
Priority: 
M – Must have.
S – Should have.
C – Could have.
How the Requirement IDs work; The first number is for stakeholder when it comes to FR and category when it comes to NFRs. The second and 3rd number is just for numbering the requirement.

| Requirement ID | Group of Feature | Description | Priority | Source/Stakeholder | Acceptance Criteria |
| :--- | :--- | :--- | :--- | :--- | :--- |
| FR-101 | Submission | The system must allow users to submit a service request using a category mechanism. | M | Requester | When valid details are submitted when the user clicks, save/submit then a unique ID is generated. |
| FR-102 | Tracking | The system must allow users to view the status of requests. | M | Requester | Given that the user inputs their unique ID, then the ticket status is displayed. |
| FR-103 | History | The system should allow authenticated users to view a history of their requests | S | Requester | Given that the user is logged in, when navigating to their profile, then a list of their past request should render. |
| FR-104 | Feedback | The system must provide feedback when a user’s request is updated. | M | Requester | When a request is accepted, rejected, updated or completed, the system must generate an appropriate notification for the requester. |
| FR-105 | Authentication & Registration | The system must allow requesters to register an account and authenticate before accessing account-specific functionality. | M | Requester | Given valid registration information, the system must create a requester account. Given valid registered credentials, the system must authenticate the requester. Invalid credentials must be rejected. |
| FR-106 | Attachments | The system should allow requesters to attach supported image files to a service request. | S | Requester | Given a requester creating or submitting a request, when a supported image is attached, the image must be associated with the correct service request and be retrievable by an authorised user. |
| FR-201 | Assignment | The system must allow staff to accept responsibility for a ticket. | M | Staff | Given that an unassigned ticket and the staff user clicks assign, then they must become the record owner. |
| FR-202 | Workflow | The system must allow staff to update request statuses through controlled transitions. | M | Staff | Given a ticket, if updated to a different status then the status state is saved in the database. |
| FR-203 | Staff View | The system must allow the staff to search, filter and sort request using criteria. | M | Staff | Given the staff dashboard, when filtering by criteria, then only tickets related to that criteria are displayed. |
| FR-204 | Resolution | The system must allow staff to record actions, comments or resolution information. | M | Staff | Given that a ticket is being resolved, then the staff member must input a resolution comment before closing it. |
| FR-205 | Request Details | The system must allow authorised staff to view the full permitted details of service requests relevant to them. | M | Staff | Given an authorised staff member opening an available request, the system must display the permitted request information associated with that request. |
| FR-206 | Request Closure | The system must allow authorised staff to resolve and close a service request through the controlled workflow. | M | Staff | Given an authorised staff member resolving a request, when all required resolution information has been provided and a permitted closing transition is performed, the request must be recorded as resolved or closed. |
| FR-207 | Department-Relevant Access | The system must make service requests available to authorised staff according to the request category and relevant staff responsibility or department. | M | Staff | Given a service request assigned to a defined category, authorised staff within the relevant responsibility area must be able to access it, while staff outside the authorised scope must not be able to access it. |
| FR-301 | Dashboard | The system must provide a dashboard to identify open, overdue and closed requests. | M | Management | Given that a manager accesses the dashboard, then a visual metric of active vs closed tickets should render. |
| FR-302 | Auditing | The system should support reporting on request lifecycle history for accountability. | S | Management | Given a completed ticket, then a timestamp audit log of all transitions should be viewable. |
| FR-303 | Assignment & Reassignment | The system must allow authorised management to assign or reassign responsibility for a service request to an appropriate staff member. | M | Management | Given an eligible service request and authorised manager, when a valid staff member is selected and the assignment is confirmed, that staff member must become the recorded assignee and the assignment change must be recorded. |
| FR-304 | Request Analysis | The system must allow authorised management to analyse service-request information using relevant dimensions such as category and status. | M | Management | Given an authorised manager viewing service-request information, when a supported category, status or other approved dimension is selected, the resulting information must correspond to the selected criterion. |
| FR-305 | Contact Information Authorisation | The system must restrict staff access to requester contact information and allow authorised management to control access where additional clarification is required. | M | Management | Requester contact information must not be made available to an unauthorised staff member. Where the required access has been authorised for a request, the permitted information must become available only to the appropriate authorised staff member. |

## Non-Functional Requirements
| Requirement ID | Category | Description | Measurable Acceptance criteria | Justification |
| :--- | :--- | :--- | :--- | :--- |
| NFR-101 | Security | The system must enforce authentication and data protection. | Passwords must be hashed.<br>Data in transit must use https.<br>Role-Based Access Control must prevent requesters from accessing staff endpoints.(measurable through test gates, binary pass/fail) | “Security is a lifecycle wide responsibility not a final add-on", Because CivicConnect handles sensitive community data such as locations and contact details, failing to secure trust early creates privacy risks. |
| NFR-201 | Performance | The platform must respond efficiently to user inputs to prevent duplicate submissions. | 95% of all standard API read and write requests must compile in less than 800 milliseconds under normal system load. | If the system responds slow, then users will click “submit/save” multiple times, leading to duplicated tickets. By setting a millisecond limit, gives the team a measurable goal. |
| NFR-301 | Constraints | The architecture must operate for free (open source) or within low cost. | The production environment must run on free-tier services without exceeding monthly quotas. | Cost is an engineering constraint in this Project. |
| NFR-401 | Compatibility | Given that the decision is made that the system needs to operate on multiple different platforms -The public portal must be usable on modern desktop and mobile browsers. Please note this decision will only be made in milestone 2. | The UI must pass responsive visual testing on the newest versions of Chrome, Safari, Edge and Firefox without horizontal scrolling on mobile. | Since native mobile applications are out of scope, the web interface is the only way citizens can submit a new service request. Requesters will most likely report issues on the go, using their mobile browsers, making responsiveness a crucial attribute. |
| NFR-501 | Reliability | The system must handle erroneous inputs without crashing. | 100% of the form submissions must have backend validation.<br>The system must return human readable http error codes instead of stack traces. | If the system crashes silently on bad input, tickets are lost. Validation ensures data integrity and provides feedback to the user. |
