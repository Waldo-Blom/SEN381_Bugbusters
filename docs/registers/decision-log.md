Where insufficient evidence currently exists to support a responsible decision, the decision is deliberately deferred and the information required before commitment is identified.

| DEC-001 | Requirement Identification Convention | CivicConnect requirements must remain identifiable and traceable across the PED, RTM and later engineering artefacts. The team therefore needs a consistent naming and numbering convention. | Requirements must use unique and stable identifiers and must remain traceable throughout later design, implementation, testing and change activities. | Use a single sequential numbering scheme for all requirements. <br>Separate Functional and Non-Functional Requirements and use numbering groups to indicate stakeholder or quality category. | Functional Requirements will continue to use stakeholder-based numbering, with FR-1xx for Requester requirements, FR-2xx for Staff requirements and FR-3xx for Management requirements. Non-Functional Requirements will use category-based numbering. | The numbering structure allows the team to identify the primary stakeholder or quality category associated with a requirement while maintaining stable identifiers for traceability. As the scope now contains related behaviour across Requesters, Staff and Management, this separation also reduces ambiguity when requirements are later linked to design, implementation, testing and change evidence. | The convention improves organisation and traceability but requires the team to maintain the numbering structure consistently as new requirements are added or changed. | Incorrect, duplicated or inconsistently referenced IDs could break links between the requirements tables, RTM, GitHub issues, later tests and release evidence. | Functional Requirements table, Non-Functional Requirements table and Initial RTM within PED | The same requirement IDs will be used in later architecture/design artefacts, GitHub issues and PRs, implementation evidence, tests and acceptance evidence. |
| DEC-002 | GitHub Branching Strategy | The team requires a controlled GitHub workflow that prevents uncontrolled changes to the project's stable code and documentation while allowing three team members to work concurrently. | The main branch must be protected, substantive changes must enter through Pull Requests, and changes require two approvals from team members other than the author. | Use only a protected main branch with temporary feature branches.<br>Use protected main and dev branches with temporary feature/documentation/fix branches. | The team will use main and dev as the primary controlled branches, with temporary feature branches created for individual pieces of work. Branch prefixes such as feature/ and docs/ will be used to indicate the purpose of the branch. | Separating active development from the controlled main branch provides an additional integration point while still allowing individual work to occur independently and be reviewed before it enters a controlled branch. | The additional dev branch creates more branch-management overhead and requires the team to keep merges and branch states controlled. | Poor branch management could cause merge conflicts, divergence between dev and main, or confusion about which branch represents the current controlled state.<br>Because the scope contains functionality that cuts across user roles and departments, parallel work on related features could create integration conflicts if branches remain isolated for too long. | GitHub repository configuration, branch rulesets, documented branch naming convention, branch history and Pull Request evidence. | Future implementation, testing and integration work will follow this branching structure, so GitHub history can provide traceable evidence of controlled engineering changes. |
| DEC-003 | Exclusion of High-Complexity Communication and Media Features | CivicConnect Project could support additional interaction mechanisms such as an AI chatbot, internal real-time messaging, video uploads and voice input. | The project is limited by schedule, team size, cost, storage capacity, security considerations and the requirement to prioritise the core service-request workflow. | 1. Include all proposed communication/media features. <br>2. Include selected additional features. <br>3. Exclude these features and focus on the core request workflow. | AI chatbot functionality, internal real-time messaging, video uploads and voice input will be excluded from the committed baseline. CivicConnect will use structured request information, supported image attachments and external communication such as email or telephone when further clarification is required | These additional features are not necessary to satisfy the core CivicConnect business need and would introduce additional implementation, storage, security, testing and maintenance complexity. | Users receive fewer communication/input options, but the reduced scope allows the team to focus available time and resources on the core request lifecycle, security, traceability and quality. | Some users may prefer richer communication mechanisms. However, including them could increase schedule pressure, storage requirements, integration complexity and technical debt. | PED Out-of-Scope section | Architecture, storage and interface design do not need to support video, audio, chatbot or internal real-time messaging capabilities. Adding any of these later would require formal change analysis. |
| DEC-004 | Defer Final Technology Stack and Architecture Selection | CivicConnect now has a more defined baseline that includes account authentication, departmental request routing, image attachments, management dashboards, email notifications, role-based access and responsive requester-facing interfaces. These requirements create significant implications for persistence, security, deployment, file storage and interface design. | Technology selection must consider requirement fit, team capability, learning curve, cost, security, testing support, development-environment compatibility, maintainability and deployment compatibility. | 1. Select a preferred stack and architecture immediately during M1. <br>2. Make a provisional choice based primarily on existing team familiarity. <br>3. Deliberately defer final selection until M2, when sufficient requirements and comparison evidence are available. | Deferred to Milestone 2. The team will not commit to a final technology stack or software architecture during M1. | Selecting a stack before the requirements, quality attributes and constraints are sufficiently baselined could prematurely constrain the solution and create avoidable technical, schedule, cost or deployment problems. | Deferring preserves flexibility and enables evidence-based evaluation, but technology evaluation must be completed early enough in M2 to avoid reducing implementation time. | Deciding too early could result in an unsuitable technology choice. Deferring for too long could create schedule pressure during M2 and M3. | M1 scope/constraints, Requirements and Acceptance Criteria, Forward Engineering Considerations, team-capability assessment and later M2 technology comparison evidence.<br>Future evidence list will include:<br>support for authentication and role/department-based access<br>image storage/file-size limitations<br>email notification support<br>responsive web interface support<br>database and persistence requirements<br>deployment/free-tier compatibility<br>security support<br>team familiarity and learning curve<br>test and CI compatibility | M2 must evaluate viable technology and architecture alternatives against the baselined requirements, NFRs and constraints before committing to implementation. |
| DEC-005 | Defer CI / GitHub Actions Configuration | The final system will require automated build, testing and quality controls, potentially implemented through GitHub Actions. However, the exact CI workflow depends on the technology stack, build process and testing tools selected later. | M1 establishes the engineering foundation rather than implementing the CI pipeline. The final stack and architecture have not yet been selected. | 1. Configure GitHub Actions immediately using assumed technologies. <br>2. Create only a placeholder workflow. <br>3. Defer the exact CI implementation until the build, dependency and testing requirements are known. | Deferred. The team will use CI and automated quality controls later in the project, but the exact GitHub Actions workflow will not be selected or implemented during M1. | A meaningful CI pipeline must reflect the actual technology stack, dependency installation process, build commands and automated tests. Configuring it before those are known could create throwaway work or unnecessarily constrain later choices. | Deferring avoids premature configuration but means CI setup will become an important early activity once the stack is selected. | If the CI decision is deferred too long, automated build and testing evidence may be delayed. If configured too early, the workflow may require significant rework | PED decision/deferment note; later technology decision; GitHub Actions workflow and pipeline evidence in subsequent milestones. | Once the M2 technology stack is selected, the team must define the appropriate build, test and quality checks and configure the CI workflow accordingly. |
| DEC-006 | Use Email-Based Registration Rather Than Social Login | CivicConnect requires user accounts for Requesters, Staff and Management. Account identity is also needed to associate requests, department membership, management responsibility, requester details and email notifications with specific users. | The project has limited development time and resources. Additional external authentication providers would introduce third-party API dependencies, configuration, security considerations and additional testing requirements. | 1. Email/password registration managed by CivicConnect. <br>2. Third-party/social login such as Google or Facebook. <br>3. Support both approaches. | CivicConnect will use an email-based registration and authentication mechanism. Third-party/social login will not form part of the committed baseline. | Email is already required for requester notifications and provides a single controlled identity mechanism without introducing additional external authentication integrations. | The team must manage the security responsibilities associated with authentication and password storage, while users do not receive the convenience of signing in through an existing external account. | Poor authentication or password-management implementation could expose user accounts. The selected implementation will therefore need appropriate security controls and verification. | PED In-Scope and Out-of-Scope sections; Authentication Functional Requirement; Security NFR. | M2 architecture and security design must provide an appropriate authentication mechanism, secure credential handling and role/account association. External identity-provider APIs do not need to be supported. |
| DEC-007 | Department-Based Request Access and Management-Controlled Contact Information | CivicConnect must ensure that requests are handled by relevant departments while limiting unnecessary access to request and requester information. Staff may need requester contact details when additional clarification is required. | Requests may contain sensitive contact and location information. Staff should only access requests relevant to their department, and access to requester contact information should be controlled. | 1. Allow all Staff to view and claim all requests. <br>2. Restrict requests by department but allow staff unrestricted access to requester contact information. <br>3. Restrict requests by department and require management approval before Staff gain access to requester contact information. | Service requests will be categorised and made available only to the relevant department. Staff may accept responsibility only for eligible requests within their department. Requester contact information will remain restricted until authorised by the relevant manager where additional clarification is required. | Department-based access reduces irrelevant request exposure and supports clear operational ownership. Management-controlled access to contact information limits unnecessary exposure of requester data while still allowing Staff to obtain clarification when justified. | The approach introduces additional permissions, approval logic and management involvement compared with allowing unrestricted access. It may also slightly delay Staff access to requester contact information. | Incorrect category assignment could make a request unavailable to the correct department. Poorly implemented access controls could either block legitimate Staff or expose requester information to unauthorised users. | PED In-Scope section; Stakeholder Analysis; FR-207 Department-Relevant Access; FR-305 Contact Information Authorisation; NFR-101 Security. | M2 architecture and data design must support user roles, department relationships, request-category mapping, authorisation rules and controlled access to requester information. M3 testing must verify both permitted and denied access scenarios. |
| DEC-008 | Partial Mobile Responsiveness Scope | CivicConnect will be used by different stakeholder groups with different interface needs. Requesters may need to submit and track service requests while away from a desktop environment, while Staff and Management interfaces are likely to contain denser operational information such as assignment controls, filtering tools and management dashboards. | The project has a limited development schedule and a three-person team. Making every interface fully responsive would increase design, implementation and testing effort. The exact mobile usability needs of Staff and Management have also not yet been sufficiently established. | 1. Make all Requester, Staff and Management interfaces fully responsive from the outset. <br>2. Provide no specific mobile adaptation and target desktop use only. <br>3. Prioritise mobile responsiveness for Requester-facing interfaces and defer the extent of mobile adaptation for Staff and Management interfaces until their needs and screen complexity are better understood. | Requester-facing functionality will be designed to support mobile browser use. The extent of mobile responsiveness for Staff and Management interfaces is deliberately deferred until further analysis of their operational needs and interface requirements has been completed. | Requesters are more likely to need convenient access when submitting, tracking or reviewing requests from different locations. Staff and Management interfaces may require larger or information-dense screens and committing to full responsiveness before the relevant layouts and workflows are understood could introduce unnecessary development and testing effort. | Prioritising Requester mobile usability reduces immediate responsive-design effort and allows the team to focus on the most likely mobile-use case. However, Staff and Management may have a less optimised mobile experience if later analysis does not justify additional responsive design. | If Staff or Management later require significant mobile access, additional redesign and testing may be necessary. Conversely, attempting to make all interfaces fully responsive too early could increase schedule pressure and reduce time available for higher-priority functionality and quality controls. | PED In-Scope section under Digital Platform Mobile Accessibility; Deferred Scope section under Extent of Mobile Adaptability; NFR-401 Compatibility; later M2 wireframes/prototypes and stakeholder/interface analysis. | M2 user-interface design must prioritise responsive behaviour for Requester-facing screens. Staff and Management mobile requirements must be reviewed before their interface designs are finalised. NFR-401 may need to be refined so its measurable acceptance criteria clearly state which stakeholder interfaces and screen sizes are required to support responsive use. |
