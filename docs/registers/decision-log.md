This Engineering Decision Log records significant decisions made throughout the project so that their rationale, trade-offs, risks and later consequences remain traceable. Where insufficient evidence exists to support a responsible decision, the decision is deliberately deferred and the information required before commitment is identified. Where an earlier decision is later resolved or amended, the original decision remains traceable through its Later Consequence entry.

| DEC-001 | Requirement Identification Convention | CivicConnect requirements must remain identifiable and traceable across the PED, RTM and later engineering artefacts. The team therefore needs a consistent naming and numbering convention. | Requirements must use unique and stable identifiers and must remain traceable throughout later design, implementation, testing and change activities. | 1. Use a single sequential numbering scheme for all requirements.<br>2. Separate Functional and Non-Functional Requirements and use numbering groups to indicate stakeholder or quality category. | Functional Requirements will continue to use stakeholder-based numbering, with FR-1xx for Requester requirements, FR-2xx for Staff requirements and FR-3xx for Management requirements. Non-Functional Requirements will use category-based numbering. | The numbering structure allows the team to identify the primary stakeholder or quality category associated with a requirement while maintaining stable identifiers for traceability. As the scope now contains related behaviour across Requesters, Staff and Management, this separation also reduces ambiguity when requirements are later linked to design, implementation, testing and change evidence. | The convention improves organisation and traceability but requires the team to maintain the numbering structure consistently as new requirements are added or changed. | Incorrect, duplicated or inconsistently referenced IDs could break links between the requirements tables, RTM, GitHub issues, later tests and release evidence. | Functional Requirements table, Non-Functional Requirements table and RTM within the PED. | The same requirement IDs will continue to be used in architecture/design artefacts, GitHub issues and PRs, implementation evidence, tests and acceptance evidence. |

| DEC-002 | GitHub Branching and Review Strategy | The team requires a controlled GitHub workflow that prevents uncontrolled changes to stable code and documentation while allowing three team members to work concurrently. During M2, automated CI and the need for controlled progression toward staging required the original M1 branching strategy to evolve. | The main branch must remain highly protected. Changes must enter controlled branches through Pull Requests. However, requiring two independent reviewers for every development-level change creates a bottleneck for a three-person team. | 1. Retain only main and dev with two approvals on all protected branches.<br>2. Retain main and dev but reduce approval requirements for dev (main remains unchanged).<br>3. Introduce testing and staging branches and apply stronger controls as code moves closer to release. | The project will use main, staging, testing and dev as controlled branches, together with temporary feature/documentation/fix branches. main and staging require 2 independent approvals. dev and testing require 1 independent approval. The testing branch additionally requires the CI status check to pass before merging. | The revised approach preserves peer review while reducing collaboration bottlenecks during active development. Stronger controls are applied as code progresses toward staging and production. | More branches increase branch-management and promotion overhead, while reduced approvals on dev and testing provide less manual review than main and staging. | Poor branch management may cause divergence, merge conflicts or confusion about which branch represents the current integration state. Reducing approvals also increases reliance on CI and effective peer review. | GitHub branch rulesets, protected branch configuration, Pull Request history, Section 14.1 and CI evidence. | M2 Amendment: The original M1 main + dev strategy has been expanded. The testing branch is now the current code-integration branch and requires one independent approval plus successful CI. The staging branch exists but its deployment integration remains deferred to M3. |

| DEC-003 | Exclusion of High-Complexity Communication and Media Features | CivicConnect could support additional interaction mechanisms such as an AI chatbot, internal real-time messaging, video uploads and voice input. | The project is limited by schedule, team size, cost, storage capacity, security considerations and the requirement to prioritise the core service-request workflow. | 1. Include all proposed communication/media features.<br>2. Include selected additional features.<br>3. Exclude them and focus on the core request workflow. | AI chatbot functionality, internal real-time messaging, video uploads and voice input remain excluded from the committed baseline. | These features are not necessary to satisfy the core CivicConnect business need and would introduce additional implementation, storage, security, testing and maintenance complexity. | Users receive fewer communication/input options, but the team can focus resources on the core request lifecycle, security, traceability and quality. | Some users may prefer richer communication mechanisms. Adding them later would increase scope and would require formal change analysis. | PED Out-of-Scope section. | Architecture, storage and interface design do not need to support video, audio, chatbot or internal real-time messaging functionality. |

| DEC-004 | Defer Final Technology Stack and Architecture Selection | During M1, CivicConnect had identified authentication, departmental routing, image attachments, dashboards, notifications, role-based access and responsive requester-facing interfaces, but insufficient evidence existed to responsibly commit to a final architecture and technology stack. | Technology and architecture selection had to consider requirement fit, team capability, learning curve, cost, security, testing support, maintainability and deployment compatibility. | 1. Select a preferred stack and architecture immediately in M1.<br>2. Make a provisional selection based mainly on familiarity.<br>3. Defer final selection until M2. | During M1, the final technology stack and architecture were deliberately deferred to M2. | Deferring prevented premature commitment before requirements, ASRs and constraints were sufficiently established. | Deferral preserved flexibility but reduced the time available for implementation once the choices had to be finalised. | Deferring too long could create schedule pressure, while deciding too early could result in an unsuitable solution. | M1 PED scope, constraints, requirements and forward-engineering considerations. | M2 Resolution: This decision is now resolved. CivicConnect has selected a Modular Monolith architecture and a JavaScript-centric MVC technology stack consisting of Node.js v24, Express.js, EJS, Tailwind CSS, PostgreSQL and node-postgres. See DEC-009, DEC-010 and DEC-011. |

| DEC-005 | Defer CI / GitHub Actions Configuration | During M1, the final build process, technology stack and testing framework had not yet been selected, so configuring CI at that stage would have relied on assumptions. | The CI workflow must correspond to the actual runtime, dependency installation process, testing framework and quality checks used by CivicConnect. | 1. Configure GitHub Actions during M1 using assumed technologies.<br>2. Create only a placeholder workflow.<br>3. Defer exact CI implementation until the technology stack was known. | During M1, CI implementation was deliberately deferred. | This avoided configuring a workflow that might later require significant rework. | Deferral delayed automated quality evidence but avoided throwaway implementation. | Delaying CI too long could allow defects or inconsistent code to enter integration branches without automated checks. | M1 decision log and M2 CI implementation evidence. | M2 Resolution: GitHub Actions is now implemented as the initial CI quality gate. Node.js v24 is pinned through .nvmrc; npm ci installs dependencies; ESLint/Prettier performs static checks; and Jest executes automated tests. The CI status check must pass before merging into testing. Production Continuous Deployment remains deferred to M3. |

| DEC-006 | Use Email-Based Registration Rather Than Social Login | CivicConnect requires user identity for authentication, requester ownership, staff/management roles, department membership and email notifications. | External authentication providers introduce additional APIs, configuration, security considerations and testing requirements. | 1. CivicConnect-managed email/password registration.<br>2. Third-party/social login.<br>3. Support both approaches. | CivicConnect will use an email-based registration and authentication mechanism. Social login will not form part of the committed baseline. | Email is already required for notification functionality and provides a single controlled identity mechanism without an additional external identity-provider dependency. | The team must manage credential security and password handling directly. | Poor authentication or password-management implementation could expose user accounts. | Authentication Functional Requirement, Out-of-Scope section and NFR-101. | Architecture and implementation must support secure credential handling, server-side authentication and role/account association. |

| DEC-007 | Department-Based Request Access and Management-Controlled Contact Information | CivicConnect must limit service-request visibility according to operational responsibility while protecting requester contact information. | Requests may contain sensitive contact and location information. Staff should only access requests relevant to their department. | 1. All Staff may view all requests.<br>2. Restrict requests by department but allow unrestricted requester-contact access.<br>3. Restrict requests by department and require Management approval for requester contact details. | Requests are made available only to the relevant department. Staff may accept responsibility only for eligible requests within that department. Requester contact information remains restricted until authorised by the relevant manager. | This reduces unnecessary exposure of requester information while supporting operational ownership. | The approach introduces additional permissions, approval logic and Management involvement. | Incorrect categorisation could route requests incorrectly. Incorrect access-control implementation could either expose requester information or block legitimate users. | FR-207, FR-305, NFR-101 and the M2 persistence model. | M2 data design now represents roles, departments, assignments, category routing and contact-information approval. M3 must implement and verify allowed and denied access cases. |

| DEC-008 | Partial Mobile Responsiveness Scope | Requesters are likely to submit and track requests from mobile devices, while Staff and Management screens may contain denser operational information. | Full responsiveness across all roles would increase design and testing effort within the limited project schedule. | 1. Make every interface fully responsive.<br>2. Target desktop only.<br>3. Prioritise Requester-facing responsive design and defer Staff/Management mobile scope. | Requester-facing functionality will support mobile browser use. The extent of Staff and Management mobile responsiveness remains deferred. | Requesters have the strongest immediate need for mobile access, while Staff and Management interfaces are likely to require denser desktop-oriented layouts. | Staff and Management may have a less optimised mobile experience. | Later evidence may show that Staff or Management require more mobile functionality, causing additional redesign. | NFR-401, In-Scope Mobile Accessibility and Deferred Scope. | Requester-facing responsive behaviour remains part of implementation. Staff and Management mobile scope must be revisited when their final workflows and interfaces are better established. |

| DEC-009 | Select Modular Monolith Architecture | CivicConnect requires clear responsibility boundaries for authentication, request processing, workflow, auditing, notifications and reporting, while being implemented by a three-person team under a limited schedule. | The architecture must support ASR-01 to ASR-05, remain low-cost, avoid unnecessary deployment complexity and support maintainability and testing. | 1. Traditional Layered Monolith.<br>2. Microservices / Distributed Architecture. | CivicConnect will use a Modular Monolith architecture. It will remain a single deployable application while major responsibilities are separated into internal modules. | The Modular Monolith provides stronger internal separation than a basic monolith without introducing the network, deployment and data-consistency complexity of microservices. | Individual modules cannot be independently deployed or scaled. | If internal boundaries are not maintained, the application could gradually become tightly coupled. A failure in the single application process may also affect the complete system. | Architecture comparison, Sections 5.1-5.6, architecture diagrams and architecture ADR. | M3 implementation must preserve the defined internal boundaries between presentation, request handling, business rules, persistence and supporting services. |

| DEC-010 | Select PostgreSQL as the Relational Persistence Technology | CivicConnect must reliably persist users, requests, assignments, workflow history, comments, audit information and departmental relationships. | The persistence technology must support relational integrity, transactions, concurrency protection, efficient queries and low-cost deployment. | 1. Relational PostgreSQL persistence.<br>2. A document-oriented database.<br>3. Simplified file/in-memory persistence. | CivicConnect will use PostgreSQL as its persistent relational database and node-postgres as the database access layer. | PostgreSQL supports relational constraints, transactions, row-level locking and the structured relationships needed for CivicConnect's request lifecycle and access-control model. | PostgreSQL introduces reliance on a managed database environment for production and requires appropriate schema and transaction design. | Poor transaction or concurrency handling may result in lost updates or inconsistent request state. Provider-specific storage and recovery capabilities may also be insufficient. | Section 6 Data & Persistence Baseline, ERD/schema and technology-selection section. | M3 implementation must connect the application to PostgreSQL and implement transaction and concurrency controls. The database technology is decided, but the managed provider remains deferred between candidates such as Neon and Supabase. |

| DEC-011 | Select JavaScript-Centric MVC Technology Stack | The project requires a practical web technology stack that the three-person team can implement and maintain within the milestone schedule while supporting authentication, database access, responsive pages, testing and deployment. | The stack must remain maintainable, low-cost, lightweight enough for limited hosting environments and compatible with the team's capability. | 1. React/Next.js SPA with separate API backend.<br>2. Java Servlets / Spring Boot.<br>3. JavaScript-centric server-rendered MVC application. | CivicConnect will use Node.js v24, Express.js, EJS, Tailwind CSS and node-postgres as its primary application stack. | A unified JavaScript stack reduces learning and integration overhead. Server-side rendering avoids a separate frontend deployment and reduces unnecessary client-side state complexity. | EJS provides a less dynamic client experience than a SPA architecture and generally relies more heavily on full-page server-rendered interactions. | Poor separation of responsibilities could still produce tightly coupled code even within an MVC structure. Runtime or dependency differences could also create environment inconsistencies if versions are not controlled. | Section 7 Technology Stack Decision; ADR-004; .nvmrc; package.json; application repository. | Node.js v24 is pinned through .nvmrc. M3 implementation will continue using the selected Express/EJS structure and PostgreSQL integration rather than introducing a separate SPA frontend. |

| DEC-012 | Decouple Core Request Transactions from External Side-Effects | Status changes and request-resolution operations must update persistent CivicConnect state, but may also trigger secondary behaviour such as email notifications and audit processing. | Failure or delay in an external service such as SMTP must not cause a valid request-state transaction to fail or remain open unnecessarily. | 1. Direct synchronous service orchestration.<br>2. Observer / Event-Based internal side-effect handling. | CivicConnect will use an Observer / Event-Based Approach for secondary side-effects. RequestWorkflowService commits the primary transaction first, then publishes an in-memory event which supporting listeners such as NotificationService and AuditLogService respond to. | This keeps the core request state independent from slower or less reliable supporting functions. | In-memory events are lightweight but are not durable across application-process failure. | An event may be lost if the Node.js process fails after the database commit but before listeners complete. Notification failures may therefore occur even though the underlying request state is correct. | Initial Design Decision 1; ADR-005; src/services/emailService.js structural stub; RSK-013. | M3 must implement the EventEmitter-based behaviour and ensure that email/audit failures do not roll back valid request transactions. The platform remains the source of truth even if a notification fails. |

| DEC-013 | Centralise Request Lifecycle State Mutation | The request lifecycle includes controlled transitions such as SUBMITTED, ASSIGNED, IN_PROGRESS, RESOLVED and CLOSED. Duplicating transition logic across controllers would increase inconsistency and security risk. | Workflow rules must remain maintainable, testable and consistently enforced across the application. | 1. State Pattern with separate state classes.<br>2. Procedural Centralised Workflow / Transition Service. | Request lifecycle changes will be controlled through a single RequestWorkflowService containing a central allowed-transition configuration / finite state machine. Controllers will delegate mutation requests to this service. | The centralised service provides consistent transition validation without the additional boilerplate of separate state classes for a relatively small fixed lifecycle. | The service may become too dense if too many responsibilities are added. | A poorly structured central service could become a new monolithic component. | Initial Design Decision 2; ADR-006; src/services and src/controllers structure. | Validation rules should be extracted where appropriate so that RequestWorkflowService remains an orchestrator rather than accumulating unrelated logic. All request state mutations in M3 must pass through this controlled boundary. |

| DEC-014 | Select Nodemailer with SMTP as the Application-Level Email Integration | FR-104 requires requesters to receive feedback when request status changes. The email mechanism must integrate with the Node.js application without creating unnecessary architectural complexity. | The solution should remain low-cost, configurable across environments and independent from the core request transaction. | 1. Managed REST-based transactional email API.<br>2. Broker-based asynchronous messaging.<br>3. Direct SMTP integration using Nodemailer. | CivicConnect will use Nodemailer with SMTP as its application-level email integration mechanism. Ethereal will be used for development/testing. | Nodemailer integrates naturally with Node.js, introduces minimal vendor-specific application logic and allows SMTP configuration to vary between environments. | Direct SMTP depends on hosting-provider networking restrictions and SMTP-provider reliability. | Current deployment research shows that Render Free blocks outbound SMTP and Railway restricts SMTP to higher plans. Therefore the current production SMTP direction may conflict with low-cost hosting constraints. | Section 9 Initial API / Integration Decisions; ADR-005; deployment compatibility research; RSK-008 and RSK-013. | The application-level mechanism is selected, but the final production email provider/configuration remains deferred to M3. The production solution must be proven compatible with the selected host. |

| DEC-015 | Establish Deployment Environment Progression and Single-Instance Baseline | CivicConnect must progress from local development toward production without assuming that behaviour proven locally or in CI automatically proves production compatibility. | The team has limited infrastructure capacity and must avoid premature commitment to a paid or incompatible cloud environment. | 1. Deploy directly from development to production.<br>2. Introduce a containerised/distributed deployment pipeline immediately.<br>3. Progress through controlled environments before production commitment. | CivicConnect will use the progression Development -> Test/CI -> Local Staging -> Production. The current deployment baseline is a single application instance, consistent with the Modular Monolith architecture. | Local staging allows the team to validate the integrated application, configuration, database connectivity and supporting services before selecting and committing to production infrastructure. | This introduces an additional staging step and delays final cloud-provider selection. | Environment-specific configuration differences may cause behaviour that works in development or CI to fail in staging or production. | Section 10 Deployment Compatibility, RSK-014 and Section 15 Architecture, Technology and Initial Design Baseline. | Render and Railway remain candidate production application hosts, while Neon and Supabase remain candidate PostgreSQL providers. Final hosting, database provider, attachment storage, production email configuration, production secrets, Continuous Deployment, monitoring, recovery validation and horizontal scaling remain deferred until M3 evidence is available. |
