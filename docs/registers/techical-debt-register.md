## Technical Debt Register
Technical debt is recorded by type so that the cause, consequence and management approach remain traceable. Each item links to the GitHub Issue, risk register entry or architectural decision that created or governs it.

| ID | Type of Technical Debt | Item | Description | Origin | Impact | Current Mitigation | Recommended Action |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| TD-01 | Documentation | Registers out of sync with release branch | The live engineering registers (AI Usage, Risk, Decision Log, RTM) are maintained on main, while the M3 release candidate and its code reside on staging. The staging branch does not carry the most current register versions. | Deliberate branch separation: main is treated as the production/documentation baseline; staging is the release candidate branch. | Reviewers inspecting the release branch see a documentation snapshot that predates the latest register updates. | Registers are version-controlled on main; links to the live documents are embedded in the PED. | Merge main documentation into staging at release promotion, or adopt a single source of truth (e.g. publish registers from main only and link from both branches). |
| TD-02 | Code & Implementation | Operator cannot edit logged requests | Operators receive HTTP 403 when attempting to edit a request they created. The authorisation check does not recognise the operator as an authorised editor. | Access-control logic in requests.attachments.model.js and requests.service.js does not include an operator-ownership path for edit. | Blocks a core operational workflow (Issue #122, urgent). Operators cannot correct mistakes and may create duplicate requests. | Documented as GitHub Issue #122 (urgent); duplicate-request risk noted. | Extend the edit authorisation predicate to allow the operator who created the request when status is Submitted. Add tests for authorised/denied edit. |
| TD-03 | Code & Implementation | Export log button not implemented | The Manager "Export log" button on the Reporting & Audit screen is present but has no server-side endpoint. | UI placeholder; export endpoint never implemented. | Managers cannot extract audit data for reporting or compliance (Issue #121, medium). | Button exists but produces no usable export. | Implement a CSV export endpoint respecting department scope and active filters. Add unit + integration tests. |
| TD-04 | Code & Implementation | Password reset incomplete | The login screen links to a reset page, but no end-to-end flow exists (no token generation, no email, no password update). | Password-reset page was scaffolded early; full flow deferred. | Users who forget their password cannot recover their account (Issue #123, high). | Page exists as UI only. | Implement request form, single-use expiring token, email dispatch via existing notification service, password policy validation, and tests for valid/expired/reused/unknown-account flows. |
| TD-05 | Code & Implementation | Timezone handling is a temporary patch | Display code forces Africa/Johannesburg on legacy timestamp without time zone columns that store UTC wall time. SQL uses LOCALTIMESTAMP in several modules. | Neon database host in Virginia (UTC) vs South African team; legacy schema uses timestamp not timestamptz. | Users outside SA see SAST times; duration calculations may be fragile across DST boundaries (Issue #125, low). | src/shared/datetime.js centralises conversion; documented in docs/timestamps.md. | Migrate event columns to timestamptz, update SQL display conversions, and write timestamps explicitly as UTC instants. |
| TD-06 | Architecture & Design | In-memory event bus | eventBus.js extends Node's EventEmitter; audit and notification events are not durable. | Observer pattern selected in ADR-005 to decouple side-effects; persistent queue rejected as over-engineering. | If the process crashes after a DB commit but before listeners execute, the email/audit event is lost (RSK-019). | Core business operation (DB commit) is not rolled back; failures are logged. | Introduce a transactional outbox table in PostgreSQL to guarantee at-least-once delivery for audit and notification events. |
| TD-07 | Architecture & Design | Single-instance deployment baseline | The application is designed as a single-instance modular monolith; horizontal scaling and external session storage are deferred. | Deliberate architecture decision (DEC-009, DEC-015) to keep operational complexity proportionate. | Cannot scale horizontally without moving sessions out of process memory. | Single instance is sufficient for the expected low-to-medium workload. | Re-evaluate only when workload evidence shows the single instance is insufficient; then externalise session storage and consider multiple instances. |
| TD-08 | Test | Mocked DB in unit tests | Unit tests mock pg and the model layer; SQL correctness is not verified by unit tests. | Unit test isolation strategy. | SQL regressions are only caught by integration tests (which require DATABASE_URL). | Integration tests run against real PostgreSQL in CI when the secret is configured. | Maintain integration coverage for all new SQL; avoid adding untested raw queries. |
| TD-09 | Test | Performance testing kept outside staging | Due to time constraints, the team focused on deploying CivicConnect's core functionality. PT-001 has been implemented and executed on a dedicated branch from staging, but is not integrated into staging verification or CI. | Deliberate delivery-time trade-off to preserve the M3 staging baseline. Subsequent Render-hosted PT-001 passed with p95=453.98 ms and 191/191 persisted. The change has not yet been integrated into staging as of yet. | Manual execution is required; future performance regressions may not be detected automatically. | PT-001 test script, recorded execution results and persistence reconciliation. | Review implementation and integrate through a reviewed PR. Status: Open, integration deferred. |
| TD-10 | Infrastructure & Deployment | SMTP blocked on Render free tier | Outbound SMTP ports 25/465/587 are blocked on Render Free. Gmail SMTP cannot deliver from staging. | Free-tier hosting restriction (RSK-016, Issue #124, urgent). | Requesters receive no email notifications in staging. | Email flow verified locally with Ethereal and Gmail; failures do not roll back DB transactions. | Upgrade to a paid Render plan, switch to an HTTPS transactional email API, or select a host that permits SMTP. |
| TD-11 | Infrastructure & Deployment | No production monitoring/observability | Only /health exists. No centralised logging, alerting or uptime monitoring. | Observability excluded from M2/M3 CI scope. | Failures in production would not be detected proactively. | /health endpoint and host-level logs. | Add structured logging, error alerts and uptime monitoring after production host selection. |
| TD-12 | Infrastructure & Deployment | Neon cold-start latency | Neon Free scales to zero after inactivity; first request may take 1–3 s. | Serverless PostgreSQL free-tier behaviour (RSK-018). | First page load after idle may exceed NFR-201 target. | connectionTimeoutMillis: 10000; /health can warm the instance. | Monitor cold-start latency in staging; consider keep-alive pings or an always-on database instance if it degrades UX. |
| TD-13 | Security | Password reset not implemented | Users cannot recover a forgotten password; no token-based reset flow exists. | Feature deferred (Issue #123, high). | Users are locked out; support burden increases. | Login page links to a placeholder reset page. | Implement the full token-based reset flow with rate limiting and single-use expiry. |
