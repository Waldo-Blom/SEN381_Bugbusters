# PT-001 — Concurrent Service Request Submission

Status: **executed on 16 October 2026 with owner authorisation** in two environments using the
approved Neon Staging database. The local full run persisted 90/90 submissions but failed the
800 ms latency threshold (p95 3,046.85 ms). The subsequent Render-hosted full run persisted
191/191 submissions, recorded no submission errors and passed (p95 453.98 ms). Render sanity also
passed (4/4 persisted, p95 752.43 ms). The tested Render application commit differs from the local
test commit; both are recorded in [the evidence](evidence/request-submission-evidence.md).
Future executions still require explicit authorisation for their target and workload.

## Purpose and traceability

One HTTP-level k6 scenario exercises requester submission (FR-101), with existing authentication
(FR-105/NFR-101). Concurrent writes matter because slow or failed submissions can encourage retries
and lose citizen reports. This is a small SEN381 M3 Area F exercise, not a capacity certification.

[NFR-201](../../docs/requirements.md) specifies 95% of standard API reads and writes below 800 ms
under normal system load. The script applies `pt_submission_ms: p(95)<800` to submission POSTs.
The requirement does not define normal load. The proposed five-user workload is an interpretation
to review, not an approved definition of normal load, and this single endpoint cannot establish
compliance for all reads and writes. Zero submission errors and at least one attempt are additional
PT-001 functional validity gates, not newly invented performance requirements. Persistence and
interruption reconciliation are manual gates before a final pass may be recorded.

## Inspected application workflow

- Root-mounted `requests.routes.js`: `GET /requester/submit`, `POST /requester/submit`.
  `requireRole('requester')` requires a session user ID, email and requester role.
- Login: form-encoded `POST /auth/login` with `email`, `password`; successful requester login is
  `302 Location: /requester/my-requests`. The server regenerates the session. No login CSRF token is
  implemented in the current application. The script does not change this behaviour.
- Session: signed `connect.sid`, HttpOnly, SameSite=lax, eight-hour expiry, secure in production;
  server uses the default in-memory session store. Restarts lose sessions; multi-instance hosting
  can affect authentication. Record the actual test deployment configuration.
- Submission uses `parseImages`, then CSRF validation for multipart requests. The browser form
  includes `_csrf`, obtained from the GET form. The script deliberately uses multipart, retains
  the CSRF token and sends no images. Express also parses JSON and URL-encoded input; this test
  follows the browser's protected multipart path rather than taking those alternate paths.
- Fields: existing active `categoryId` UUID; nonempty trimmed `title` (max 200), `description`,
  `location` (max 255); `priority` LOW/MEDIUM/HIGH/URGENT (default MEDIUM). Use MEDIUM here.
- Controller `submitRequest` → service `submit` / `createServiceRequest` → model `create`.
  Validation errors render the form with 400; missing session 401; wrong role/CSRF 403; unexpected
  errors flow to the error handler (normally 500). Successful submission redirects with 302 to
  `/requester/my-requests`. The script disables redirects so login/error pages cannot masquerade
  as success. It checks both status and exact Location.
- Database: active-category lookup, pool acquisition (`max: 5`, 10-second connection timeout),
  transaction BEGIN, year-specific advisory transaction lock, MAX request-number sequence query,
  insert into `service_requests`, COMMIT/release. Request ID is generated by PostgreSQL and
  reference is `CC-<year>-<sequence>`. Requester and creator reference `users`; category references
  `request_categories`, which maps to `departments`. This path does not insert external requesters,
  status-history rows or assignment records. Attachments would add storage/rows, but are excluded.
- Current notification/audit listeners respond to status changes/assignment events; this creation
  path emits neither. No submission email is called. Nevertheless verify the deployed revision,
  database triggers and external automations, and use synthetic accounts with notifications off
  and test-only/sink email destinations. Do not run if real recipients can be contacted.
- Duplicate guard: same session/user/category/title/location within three seconds returns the
  same success redirect without another insert. No general submission rate limiter was found.
  Every payload title is `PT001-<runId>-vu<N>-i<N>` to avoid this guard and enable reconciliation.
- Existing suites use Jest/Supertest (unit, integration, functional, e2e). This standalone script
  is outside their configured matches and has no npm dependency or CI hook.

## Workload and measurements

Default: 0→5 VUs over 10 seconds, hold 60 seconds, 5→0 over 10 seconds (80 seconds planned),
random 1–2 second sleep after each POST. Sanity mode uses 1 VU, 1/5/1 seconds. These are two sizes
of the same scenario. Configure `PT_VUS`, `PT_RAMP_SECONDS`, `PT_STEADY_SECONDS`, `PT_DOWN_SECONDS`,
`PT_PACE_MIN_SECONDS`, `PT_PACE_MAX_SECONDS` to reduce the workload. Values must be positive.
Do not override k6 VUs/scenarios independently of the script's account allocation.

Setup logs in each distinct test account once, obtains its form/token/category and transfers its
cookie into the corresponding VU jar. Cookies persist between iterations. Setup never submits a
request. Setup calls appear in built-in k6 HTTP metrics but **not** the `pt_*` submission metrics.
Setup failure blocks the run. Sessions/tokens are held in memory; never enable `--http-debug`,
dump setup data, or export environment variables. k6 is not an npm package in this repository.

`pt_attempted`, `pt_successful`, `pt_failed`, `pt_success_rate`, `pt_error_rate`, and
`pt_submission_ms` provide counts, rates, average, median, p90, p95 and maximum. `pt_outcomes`
distinguishes HTTP success pending persistence, validation, authentication, authorisation-or-CSRF,
server errors, timeouts (k6 code 1050), other transport failures, rate limiting and unexpected
responses. 403 cannot reliably distinguish expired permissions from invalid CSRF without private
server evidence. A 200 form/error page is an unexpected failure. No failed operation is retried.

Response duration is k6 HTTP send/wait/receive time, excluding connection/TLS establishment,
authentication, redirect GET, browser rendering and pacing. All POST outcomes enter the latency
trend (including failures); interpret latency together with errors. It is a protocol measurement,
not full browser response time. No warm-up submissions are made. Record cold starts separately.

There is up to 35 seconds of graceful completion during ramp-down/end, plus setup time. Actual
wall time can exceed 80 seconds. Summaries expose interrupted/unaccounted attempts; an interrupted
request may still commit. Such a run needs reconciliation and cannot be marked passed unchanged.
Throughput fields divide attempts/successes by k6 overall elapsed seconds including setup/grace;
they are conservative overall rates, not steady-state throughput. Optional tagged JSON time-series
can support a time-window analysis. Closed-loop VUs slow their submission rate as responses slow;
this is not a fixed arrival-rate or peak-capacity test.

## Manual environment preparation (owner)

1. In VS Code confirm branch `staging_test/performance_test`, review these files, and record the
   tested commit plus uncommitted diff. Do not merge into staging yet.
2. Identify and approve an isolated application **and its actual database**. A staging name alone
   proves nothing. Confirm no production data, recipients, storage or integrations are connected.
3. If needed, manually create a dedicated Neon test branch using schema-only/synthetic data;
   select the correct project/parent deliberately and verify isolation in the Neon Console.
   Do not copy real citizen rows. Apply the existing application schema using your normal reviewed
   setup process; no schema change is required by PT-001. Provision five distinct active requester
   accounts (one for sanity), and an active category. Record their test IDs privately.
4. If hosted execution is chosen, manually configure a separate Render test web service using the
   reviewed branch, the repository's normal build/start commands, its own SESSION_SECRET and the
   isolated Neon DATABASE_URL. Configure test-only integrations and notifications. Do not change
   production/staging services. Record region, plan, instance count, commit, environment, sleep/
   cold-start behaviour, pool settings and database compute. Check secure cookies/HTTPS work.
   A local application is also allowed only when its database and side effects are approved.
5. Verify manually in the approved environment that designated accounts have requester access and
   the category is active. Do not use actual citizen credentials. The script handles login and CSRF;
   no browser cookie copying is needed. Approval is required for any application requests.
6. Record approval and isolation evidence, then set the runtime confirmation variables below.
   These flags are operator safeguards, not proof that a target is safe. Review the actual origin
   and dependencies before setting them. This implementation does not create cloud resources.

## Windows PowerShell execution

Run from repository root. Install only if needed (owner action), then open a new terminal:

```powershell
winget install --id GrafanaLabs.k6 --exact --source winget
k6 version
git branch --show-current
git status --short
# Offline JavaScript syntax check (no HTTP and no database access):
Get-Content -Raw tests/performance/request-submission.js | node --input-type=module --check
```

Configure a reviewed target, category and fresh run ID. Replace placeholders locally; do not save
secrets in committed files, console transcripts, screenshots or evidence. Credentials are prompted
without echoing passwords and serialized only into the current process environment:

```powershell
$env:PT_BASE_URL = 'https://YOUR-APPROVED-TEST-HOST'
$env:PT_CATEGORY_ID = 'YOUR-ACTIVE-CATEGORY-UUID'
$env:PT_MODE = 'sanity'
$env:PT_RUN_ID = 'sanity-' + (Get-Date -Format 'yyyyMMdd-HHmmss-fff')
$ptAccounts = @(1..5 | ForEach-Object {
    $ptCredential = Get-Credential -Message "Designated requester test account $_"
    @{ email = $ptCredential.UserName; password = $ptCredential.GetNetworkCredential().Password }
})
$env:PT_ACCOUNTS_JSON = ConvertTo-Json -InputObject $ptAccounts -Compress
# Offline k6 configuration/compilation inspection; does not call setup or send HTTP:
k6 inspect --include-system-env-vars tests/performance/request-submission.js
```

Only after explicit owner authorisation for the chosen target and workload:

```powershell
$env:PT_APPROVED = 'yes'
$env:PT_APPROVED_BASE_URL = $env:PT_BASE_URL
$env:PT_ISOLATION_CONFIRMED = 'yes'
k6 run --no-usage-report tests/performance/request-submission.js
$ptSanityExit = $LASTEXITCODE
Get-Content "tests/performance/evidence/$env:PT_RUN_ID-summary.json" | ConvertFrom-Json
```

Review exit code, errors and persisted data before full load. A nonzero exit is not a pass. If sanity
passes and full execution has been authorised, clear any workload overrides and run:

```powershell
'PT_VUS','PT_RAMP_SECONDS','PT_STEADY_SECONDS','PT_DOWN_SECONDS',
'PT_PACE_MIN_SECONDS','PT_PACE_MAX_SECONDS' | ForEach-Object {
    Remove-Item -LiteralPath "Env:$_" -ErrorAction SilentlyContinue
}
$env:PT_MODE = 'full'
$env:PT_RUN_ID = 'full-' + (Get-Date -Format 'yyyyMMdd-HHmmss-fff')
k6 run --no-usage-report tests/performance/request-submission.js
$ptFullExit = $LASTEXITCODE
$ptResult = Get-Content "tests/performance/evidence/$env:PT_RUN_ID-summary.json" -Raw | ConvertFrom-Json
$ptResult | Select-Object attempts,httpSuccessesPendingPersistence,failures,successRate,errorRate,responseTimeMs,successfulPerSecondOverall
$ptResult.metrics | ConvertTo-Json -Depth 10
```

Each run writes a whitelisted machine-readable `<runId>-summary.json` and prints it. Use a new ID
for every run; files with the same ID would be overwritten. The directory already exists. For
optional per-outcome/time-window evidence, add
`--out "json=tests/performance/evidence/$env:PT_RUN_ID-timeseries.json"` to that run's command.
Never publish raw output without review. Setup tags can contain infrastructure timing, but the
script never tags credentials, cookies, payloads or actual target URLs. Clear credentials afterward:

```powershell
Remove-Item Env:PT_ACCOUNTS_JSON,Env:PT_APPROVED,Env:PT_APPROVED_BASE_URL,Env:PT_ISOLATION_CONFIRMED -ErrorAction SilentlyContinue
Remove-Variable ptAccounts,ptCredential -ErrorAction SilentlyContinue
```

## Persistence, resources and interpretation

The expected redirect is only **HTTP success pending persistence**. In the approved test database,
manually run the following read-only SQL in Neon SQL Editor, replacing the synthetic run marker.
First check that the exact run prefix has zero rows **before** execution. Afterwards export the
minimal synthetic result set; do not select requester contact information. This SQL is provided
for owner review and has not been executed by Codex:

```sql
SELECT request_id, request_number, title, status, category_id, requester_id, created_at
FROM service_requests
WHERE starts_with(title, 'PT001-REPLACE-WITH-RUN-ID-vu')
ORDER BY title;

SELECT count(*) AS persisted_rows, count(DISTINCT title) AS distinct_titles,
       count(DISTINCT request_number) AS distinct_references
FROM service_requests
WHERE starts_with(title, 'PT001-REPLACE-WITH-RUN-ID-vu');
```

Compare rows and distinct titles/references to HTTP successes. Titles expose VU and iteration IDs;
verify account/category ownership and expected contiguous iteration markers for each VU. Counts
alone are supporting evidence; review the row list for omissions/duplicates. Reconcile failed or
timed-out operations too: a client timeout may occur after a commit. Any mismatch or unaccounted
attempt blocks a clean pass until explained. Keep sanitized row evidence with the run summary.
No automated cleanup is provided. Review record scope and relationships before any separately
authorised manual removal; retaining the isolated test environment is an option.

Where available, manually capture Render CPU/memory and response/error logs and Neon compute,
connections and query/resource observations over the same timestamp window. Record unavailable
metrics as unavailable; no resource measurements are implied by k6. Log review must omit secrets.

Fill [the evidence template](evidence/request-submission-evidence.md). Compare p95 with 800 ms,
record errors, threshold exit status, interrupted iterations and persistence reconciliation.
Mark BLOCKED/NOT RUN before execution, FAIL for breached gates, and PASS only after valid execution
and persistence review. Note whether resources/load plausibly represent the requirement's undefined
normal-load condition. Small samples, particularly sanity runs, do not support strong percentile
claims. Report cold and warm environment conditions honestly.

## Limits and deferred integration

This does not establish maximum capacity, simulate a municipality, prove long-term reliability,
cover other operations, or eliminate all performance risks. No attachments, rendering, email,
operator logging or status changes are exercised. Results depend on host/DB region, network, free
tier sleeping, compute, account/data volume, pool size and the serial request-number lock. The
run's data volume grows and may affect subsequent results. Record data size and fresh/reused state.

Implementation stays on the performance branch. Later review the test and evidence, refine
configuration/coverage only if justified, submit a PR into staging, complete peer review, then
consider a separately gated/manual performance workflow with isolated secrets and explicit load
approval. No regular CI integration or PR is created now. See
[TD-PERF-001](../../docs/registers/technical-debt-register.md).
